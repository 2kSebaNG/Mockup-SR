- Keep the reference welcome screen at the index route and its floating quick-access menu in a separate component; this isolates menu behavior from the presentation-only welcome content.
- People, departments and the category→department rules live in `organization.ts`; requests follow Enviada → En revisión (the contract administrator opened it in "Revisar solicitudes", `/gestionar-solicitudes`) → (ADC) Completada / Rechazado, or → (ADC delegates) En gestión → the assigned reviewer decides in "Gestión de departamento" (`/revision-departamento`); `normalizeLegacyStatus` maps rows stored before this flow (Autorizado, En revisión with a department), and `reviewStartedAt` / `delegatedAt` / `resolvedAt` record each step (who is acting comes from the URL until there is sign-in, and the server checks it is that department's member and the request's assignee). Pages share list state, the filters bar and the UI from `components/requests/request-list.tsx`, switch between the full-width table and a dashboard with `ViewToggle` (`?vista=dashboard`), and render inside `AppShell` (sidebar + header). Dashboards live in `components/dashboard/` on shared shadcn chart pieces (`dashboard-ui.tsx`: equal-height cards, KPI cards in a status tone with a share meter, `DataTable` paginated and shown as cards on phones), use the soft `--series-*` / `--status-*` tokens (badges share the status fill and its `-text` color), follow only the period (the dashboard's filters bar shows just the date control; search, status and category apply to the table and are kept for it) through `date-range-filter.tsx`: a shadcn range calendar; in the table the "Fecha de" choice lives inside its popover, in the dashboard everything sits in one row: the choice, a divider, the preset buttons and the calendar, each choice drawn as one connected group; the table keeps search, status, category and date in one row: `filters.dateField`, null meaning the view's default, due date in the table and creation in the dashboard; charts over time read the range as their axis via `periodOr`/`countOverTime`, grouped by day, week or month and cut at today, over `list.dateScope`, while snapshot charts show the requests whose date falls in it), and compute from `lib/request-metrics.ts`; only tables scroll sideways, inside the shadcn `ScrollArea` that `ui/table.tsx` wraps them in (tall dialogs use `DialogBody`); the department one uses `lib/department-stages.sample.ts` until requests have stages, and says so on screen.
- Rejecting always requires a reason (`rejectionReason`, shown to the requester), and while a request waits on a decision the contract administrator or its assigned reviewer can set `estimatedResolution`; both rules live in `requests.server.ts` as well as the dialogs. Request tables sort by `createdAt` (newest first) or `dueDate` via `sortRequests`.
- "Nueva solicitud" sends one or more items (`requestPackageSchema`); two or more become a package: individual requests `REQ-n-1`, `REQ-n-2`… sharing `parentCode` `REQ-n`, each decided on its own. There is no parent row: a package is its children (`packageChildren`, `packageProgress`), shown in `components/requests/request-package.tsx`; a reviewer only gets a package through `getReviewerPackage` when one of its requests is assigned to them.
- Requests go through `requests.functions.ts` → `requests.server.ts` (requester and contract-administrator rules) → `requests-store.server.ts`, which uses Lovable Cloud when `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` exist and otherwise, in development only, `.data/requests.json` seeded with sample requests; this keeps the UI testable locally without changing code for Cloud.
- The requirement catalog (types, selects, options) lives in `catalog-store.server.ts`; requests never write to it. What a request uses that the catalog lacks is stored as `proposal` on the request and reviewed item by item (`catalog.ts` `reviewOf`); only the contract administrator's approvals (`applyItem`, from the request detail or `/catalogo`) change the catalog, and corrected names are kept as aliases so the old names map to the approved ones.
- Every request names an element (`element`, shown under the category's `elementLabel`, e.g. "Cargo"). Master catalogs of elements per category live in `element-store.server.ts`: suggestions use pg_trgm (`search_requirement_elements`) in Lovable Cloud and the equivalent trigram ranking in `elements.ts` locally. A new element is a `proposal` item like the other catalog novelties and is only added once the contract administrator approves it (its category must exist first).
- The Catálogo page edits the catalog directly through `catalog-admin.ts` (`catalogActionSchema` → `applyCatalogAction`) and the element store; renames keep the old name as an alias, and in Lovable Cloud a renamed category keeps its row so its elements follow by cascade.
- Keep requirement catalog and validation in a shared browser-safe module, dynamic modal state in its own component, and AI extraction behind a server function using server-only Gateway helpers; this keeps private configuration out of browser bundles and proposals editable without submitting requests.
- Light / dark theme: `ThemeToggle` in the header saves the viewer's choice (`lib/theme.ts`, applied by a head script before first paint; without a choice it follows the system). The sidebar keeps its graphite in both themes; the page and header take the light background in light and the sidebar graphite in dark (`--header-*` tokens), and tooltips are black in light and white in dark (`--tooltip`). Pages that load data show skeletons from `components/requests/request-skeletons.tsx` (route `pendingComponent`, charts until they can measure, the package dialog).
- People and access follow the Human360 API (`NachoXx25/Human360API`, module Authentication: `docs/frontend-integration.md` and `specs/{auth-login,role-management,employee-invitation}`): `lib/access.ts` holds its permission catalog, roles, employees with their invitations and the session as pure operations that return the API's outcomes (message, or status + `code` + field `details`), with the same rules (scope: only act on employees whose permissions are a subset of yours and never on yourself; only grant permissions or roles you hold; Admin is a read-only system role; last admin; 72 h links, 60 s cooldown and 10 sends a day). Until the screens call the API, `lib/access-store.ts` keeps that state in localStorage seeded with sample people (password `Ecosistema#2026`). Pages: `/login`, `/recuperar-contrasena` and `/invitacion#token=…` on the shadcn login-02 block (`components/auth/`, always light on white, no theme switch, every password with an eye), `/empleados` (filters in the URL), `/empleados/$id`, `/roles`, `/roles/$id` and the `/permisos` matrix, under Recursos Humanos → Personas y accesos in the sidebar and guarded by `AccessPage` (session, then permission); logout lives in `NavUser`. Inviting an employee and creating or editing a role are modals (`InviteEmployeeDialog`, `RoleDialog`); inside the invitation a custom role is created inline under the role choices (`InlineRoleCreator`). Employee actions come from `components/access/employee-actions.tsx` (`availability` applies the API's order: permission ⇒ not yourself ⇒ scope ⇒ status): see and edit always, then deactivate / reactivate, or for pending invitations resend, change email and cancel under "…"; locked actions stay visible with the reason in their tooltip. System roles read "Name - Sistema" (`roleLabel`); the phone (+56 9 and 8 digits) is the mockup's own field until the API has one. Password recovery has no backend contract yet (`password-reset` is the next feature), so its page only shows the neutral answer.
