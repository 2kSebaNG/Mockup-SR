- Keep the reference welcome screen at the index route and its floating quick-access menu in a separate component; this isolates menu behavior from the presentation-only welcome content.
- People, departments and the category→department rules live in `organization.ts`; requests follow Enviada → (ADC) Autorizado / Rechazado, or Enviada → (ADC delegates) En revisión → the assigned reviewer decides in `/revision-departamento` (who is acting comes from the URL until there is sign-in, and the server checks it is that department's member and the request's assignee). Pages share list state and UI from `components/requests/request-list.tsx` and render inside `AppShell` (sidebar + header).
- Rejecting always requires a reason (`rejectionReason`, shown to the requester), and while a request waits on a decision the contract administrator or its assigned reviewer can set `estimatedResolution`; both rules live in `requests.server.ts` as well as the dialogs. Request tables sort by `createdAt` (newest first) or `dueDate` via `sortRequests`.
- "Nueva solicitud" sends one or more items (`requestPackageSchema`); two or more become a package: individual requests `REQ-n-1`, `REQ-n-2`… sharing `parentCode` `REQ-n`, each decided on its own. There is no parent row: a package is its children (`packageChildren`, `packageProgress`), shown in `components/requests/request-package.tsx`; a reviewer only gets a package through `getReviewerPackage` when one of its requests is assigned to them.
- Requests go through `requests.functions.ts` → `requests.server.ts` (requester and contract-administrator rules) → `requests-store.server.ts`, which uses Lovable Cloud when `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` exist and otherwise, in development only, `.data/requests.json` seeded with sample requests; this keeps the UI testable locally without changing code for Cloud.
- The requirement catalog (types, selects, options) lives in `catalog-store.server.ts`; requests never write to it. What a request uses that the catalog lacks is stored as `proposal` on the request and reviewed item by item (`catalog.ts` `reviewOf`); only the contract administrator's approvals (`applyItem`, from the request detail or `/catalogo`) change the catalog, and corrected names are kept as aliases so the old names map to the approved ones.
- Every request names an element (`element`, shown under the category's `elementLabel`, e.g. "Cargo"). Master catalogs of elements per category live in `element-store.server.ts`: suggestions use pg_trgm (`search_requirement_elements`) in Lovable Cloud and the equivalent trigram ranking in `elements.ts` locally. A new element is a `proposal` item like the other catalog novelties and is only added once the contract administrator approves it (its category must exist first).
- The Catálogo page edits the catalog directly through `catalog-admin.ts` (`catalogActionSchema` → `applyCatalogAction`) and the element store; renames keep the old name as an alias, and in Lovable Cloud a renamed category keeps its row so its elements follow by cascade.
- Keep requirement catalog and validation in a shared browser-safe module, dynamic modal state in its own component, and AI extraction behind a server function using server-only Gateway helpers; this keeps private configuration out of browser bundles and proposals editable without submitting requests.
- Visual design follows the "Sistema Base" design system (graphite, signal red and white; Barlow Condensed + Barlow): color enters only through the oklch tokens in `styles.css`, components use semantic utilities and the token for each state (`hover:bg-primary-hover`, `bg-overlay`), never palette utilities, literals or opacity on a token, and `src/test/design-system.test.ts` enforces it; destructive buttons are outlines, `destructive-solid` only confirms inside a dialog.
